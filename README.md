# Совместная работа через очередь

Общая ветка команды — `feature/team-shared`. Каждый участник работает в своей ветке `feature/имя-задача`. В `main` находится код самой очереди.

1. Начните свою ветку от актуальной `feature/team-shared`. Сделайте изменения, сохраните их коммитом и отправьте свою ветку на GitHub.
2. Откройте PR в `feature/team-shared`.
3. В [Actions → Очередь изменений](https://github.com/Tenzen1231/TestReserch/actions/workflows/queue.yml) нажмите **Run workflow**. Оставьте **Use workflow from: main**, укажите свою ветку в `source_branch` и требование в `requirement`: `discount` — скидка, `fee` — сбор, `currency` — подпись RUB. `baseline` проверяет только прежнее поведение и уже принятые требования. `legacy-rubles` — намеренно несовместимый учебный случай для проверки остановки ремонта.
4. Посмотрите статус `council/feature/team-shared#…` у вашего коммита в PR. Ссылка **Details** ведёт к решению очереди.

- **Проверяем / Ожидает публикации** — очередь ещё работает.
- **Исправляем автоматически: попытка 1/2** — `deepseek/deepseek-v4.1-flash` через RouterAI получил конфликт или провал проверки и предлагает исправление. Очередь заново проверит весь результат.
- **Принято** — именно эта версия вошла в общую ветку. **Принято ранее** — повторная отправка, нового слияния нет.
- **Отклонено: две попытки ремонта не помогли; нужен человек** — общей ветке эта заявка не навредила. Согласуйте спорное поведение и одного автора итоговой правки; остальные передают ему требования и проверяют результат. После исправления обычным новым коммитом отправьте новую заявку. Не запускайте ту же заявку по кругу.
- **Отклонено** с другой причиной — например, попытка изменить защищённый файл; такие ошибки модель не исправляет. Причина указана в статусе и запуске.
- **Ошибка** — очередь не смогла подтвердить результат. Откройте запуск; не считайте эту правку принятой. После устранения причины можно отправить её снова.

У каждого коммита свой статус: принятие старой версии не означает принятие следующего push. Зелёный запуск обычных тестов также не означает принятия очередью. Обычная кнопка Merge и прямой push в общую ветку заблокированы сервером; публикует только очередь после проверки общего результата.

Рабочие ветки и локальные изменения очередь не переписывает. Исправление входит в общий merge-коммит с исходной веткой в истории, поэтому повтор уже принятого коммита не запускает новый ремонт. Перед обновлением своей копии сохраните незавершённую работу коммитом или stash, получите актуальную общую ветку и объедините её со своей обычным merge.

Требования принятых фич хранятся в защищённом `.queue/requirements.json`. Их объединяют с требованием новой заявки. Модель может менять только продуктовые файлы, а проверки и требования берутся из доверенной версии очереди. Скидка применяется до округления цены в копейках, сбор прибавляется после него. Это позволяет проверять и каждую фичу отдельно, и их совместное поведение.

На один запуск очереди приходится максимум два исходящих запроса к RouterAI, включая сетевые ошибки и некорректные ответы. Обновление общей ветки этот бюджет не обнуляет. **Re-run jobs** не вызывает ремонт повторно; новый явный **Run workflow** создаёт новую заявку. Внутренние резервные обращения RouterAI не контролируются нашим счётчиком. Ключ `ROUTERAI_API_KEY` находится только в секрете окружения `queue-publisher`; проверяемый код запускается в контейнере без сети и секретов.

Это учебный проект: разрешены изменения в `money.py`, `receipt.py`, `email_receipt.py` и `feature_a.py`–`feature_c.py`. Для рабочего проекта нужны его собственные проверки и список разрешённых файлов. Участникам достаточно права Write; права Admin оставляют владельцу настройки. Владелец может изменить защиту репозитория, поэтому он остаётся доверенной стороной.
