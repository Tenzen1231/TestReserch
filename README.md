# Совместная работа через очередь

Общая ветка команды — `feature/team-shared`. Каждый участник работает в своей ветке `feature/имя-задача`. В `main` находится код самой очереди.

1. Начните свою ветку от актуальной `feature/team-shared`. Сделайте изменения, сохраните их коммитом и отправьте свою ветку на GitHub.
2. Откройте PR в `feature/team-shared`. В описании оставьте одну строку `Queue-Requirement: prefix`, заменив `prefix` нужным требованием из списка ниже. Шаблон PR подскажет варианты.
3. Готовый PR отправляется в очередь **сам при открытии и каждом push**. Черновики ждут отметки Ready for review. Изменение требования в описании тоже запускает проверку. Кнопку Run workflow нажимать не нужно.
4. Посмотрите статус `council/feature/team-shared#…` у вашего коммита в PR. Ссылка **Details** ведёт к решению очереди.

- **Проверяем / Ожидает публикации** — очередь ещё работает.
- **Соединяем структуру кода через Mergiraf** — Git нашёл текстовый конфликт. Mergiraf 0.20.0 пробует соединить структуру; затем проверяются все принятые требования.
- **Исправляем автоматически: попытка 1/2** — `deepseek/deepseek-v4.1-flash` через RouterAI получил конфликт или провал проверки и предлагает исправление. Очередь заново проверит весь результат.
- **Принято** — именно эта версия вошла в общую ветку. **Принято ранее** — повторная отправка, нового слияния нет.
- **Отклонено: две попытки ремонта не помогли; нужен человек** — общей ветке эта заявка не навредила. Согласуйте спорное поведение и одного автора итоговой правки; остальные передают ему требования и проверяют результат. Автор отправляет обычный новый коммит в тот же PR, и очередь запускается сама.
- **Отклонено** с другой причиной — например, попытка изменить защищённый файл; такие ошибки модель не исправляет. Причина указана в статусе и запуске.
- **Ошибка** — очередь не смогла подтвердить результат. Откройте запуск; не считайте эту правку принятой. После устранения причины можно отправить её снова.

У каждого коммита свой статус: принятие старой версии не означает принятие следующего push. Зелёный запуск обычных тестов также не означает принятия очередью. Обычная кнопка Merge и прямой push в общую ветку заблокированы сервером; публикует только очередь после проверки общего результата.

Рабочие ветки и локальные изменения очередь не переписывает. Исправление входит в общий merge-коммит с исходной веткой в истории, поэтому повтор уже принятого коммита не запускает новый ремонт. Перед обновлением своей копии сохраните незавершённую работу коммитом или stash, получите актуальную общую ветку и объедините её со своей обычным merge.

Требования принятых фич хранятся в защищённом `.queue/requirements.json`. Их объединяют с требованием новой заявки. Модель может менять только продуктовые файлы, а проверки и требования берутся из доверенной версии очереди. Скидка применяется до округления цены в копейках, сбор прибавляется после него. Это позволяет проверять и каждую фичу отдельно, и их совместное поведение.

Требования учебного проекта: `discount` — скидка, `fee` — сбор, `currency` — RUB, `prefix` — строка перед суммой, `suffix` — строка после суммы, `round-up` — округление суммы вверх до целых. `baseline` проверяет прежнее поведение и уже принятые требования; он не описывает новую фичу. Для новой фичи, которой нет в каталоге, сначала добавляют её проверку в доверенную очередь. `legacy-rubles` — намеренно несовместимый пример для проверки остановки ремонта.

Порядок: обычный Git → при конфликте Mergiraf → проверки → при оставшемся конфликте или провале проверок DeepSeek → повторная проверка → публикация. Mergiraf не подтверждает сохранение смысла сам по себе: его результат проходит те же проверки. Оба инструмента работают с копиями; ваши ветки не переписываются.

Для одной версии исходного коммита и одной общей ветки разрешены максимум два исходящих запроса к RouterAI, включая сетевые ошибки и некорректные ответы. Счётчик сохраняется **до обращения** в защищённой ветке `feature/queue-state`. Повторное событие, изменение описания PR, новый запуск очереди и обновление общей ветки этот бюджет не обнуляют. Потерянная попытка тоже расходуется. Новый коммит автора получает свой лимит; очередь сама такие коммиты в рабочую ветку не отправляет. Внутренние резервные обращения RouterAI не контролируются нашим счётчиком. Ключ `ROUTERAI_API_KEY` находится только в секрете окружения `queue-publisher`; Mergiraf и проверяемый код запускаются в контейнерах без сети и секретов.

Автоматический обработчик читает только метаданные PR и запускает доверенную очередь из `main`. Перед проверкой и публикацией очередь сверяет актуальный PR с версией из события. Старый push не подменяется новым незаметно. События `pull_request_target` разрешены отдельной Actions policy только для `.github/workflows/submit-pr.yml`.

Это учебный проект: разрешены изменения в `money.py`, `receipt.py`, `email_receipt.py` и `feature_a.py`–`feature_c.py`. Для рабочего проекта нужны его собственные проверки и список разрешённых файлов. Участникам достаточно права Write; права Admin оставляют владельцу настройки. Владелец может изменить защиту репозитория, поэтому он остаётся доверенной стороной.
